# GATE 3 — UI Design (the full procedure)

Read this when the feature has a UI and the dialogue reaches GATE 3. The gate produces a **design system**, not a one-off mockup. **Read [design-tokens.md](design-tokens.md) first** — it defines the two-tier token architecture, the seeded-variation archetype pool, the light/dark tonal rules, and the responsive breakpoints. This is what stops every project from getting the same designer's favourite UI, and what makes light/dark ONE design instead of two. The placeholders `<design-dir>`, `<state-dir>` and `<url-base>` are defined in [design-mode.md](design-mode.md).

Each numbered step that asks the user something is its own turn. End the turn at the question and wait for the answer.

**0. Ground in the current design and the platform guidelines.** Before proposing anything, inventory what the app already looks like — `.workspace/shared/brand.md`, `.workspace/shared/design-tokens.css`, the app's own stylesheet/theme files, its component library and any screenshots — and follow it: the current design is the constraint, not a suggestion, unless the user asked for a rework or said to ignore it (the only other exception is a greenfield app with no design yet). Then pick the guideline set by target platform per [design-principles.md](design-principles.md) — Android/Material web/Flutter → Material 3, Apple platforms → Apple HIG, Windows/Microsoft 365 → Fluent 2, neutral web → the app's own system (else pick one and say which) — and read the matching section of the deep lore ([#material-3](../../../lore/deep/design-principles.md#material-3), [#apple-hig](../../../lore/deep/design-principles.md#apple-hig), [#fluent-2](../../../lore/deep/design-principles.md#fluent-2), [#design-systems](../../../lore/deep/design-principles.md#design-systems); Grep `^## ` then Read offset/limit). When online, consult the live guideline page for each specific component you design (WebFetch, or `/magic` for a wider question) and paraphrase — never paste guideline text into a mockup. WebFetch is not pre-approved by this skill: each guideline fetch goes through Claude Code's normal WebFetch permission prompt. The three directions in step 1 then vary **inside** the current design's constraints; only when a rework was requested does the seed/variation rule below apply in full.

**1. Seed + three distinct directions (variation).** Silently scan existing CSS/brand assets/README/audience for tone. **If the app already has a design and no rework was requested (step 0):** skip the seed; the three directions vary only the layout *skeleton*, density and component choice inside the current tokens — same fonts, same palette, same personality. The variation rule below applies **only to a greenfield app or an explicit rework:** derive a per-run **style seed** (`openssl rand -hex 4`, else `date +%s`). Using the seed, pick **3 genuinely distinct archetypes** from the design-tokens.md pool — they must differ on **≥2 axes** (font *family*, layout *skeleton*, density, base personality). **NEVER default to** Inter/Roboto/system fonts, purple-on-white, Space Grotesk, or "clean modern SaaS" — except that a platform system font (Roboto, SF Pro, Segoe UI) is allowed whenever the chosen guideline set prescribes it. Name each font with a fallback stack; link a hosted web font (for example from Google Fonts) only when the user asks for it, because their browser then fetches it from that host (see the typography rule in [visual-companion.md](visual-companion.md)).
   - **Companion surface (B):** write `<design-dir>/screens/v1/directions.html` — three cards, each a representative layout rendered in its OWN token set, each a `data-choice`. Give the URL + a one-line description of each. End your turn; next turn read `<state-dir>/events.jsonl` for their pick.
   - **Artboard surface (A):** write the same `directions.html` to disk first (it is the durable copy). Then show the three directions as three artboards in the `/design` artifact, named the same way. Give the artifact link + a one-line description of each. End your turn. Next turn, read the user's reply (or the artifact comment) for their pick.
   - **Text mode (C):** describe the 3 directions, then call `AskUserQuestion` — *"Which direction?"* — with one option per direction (3 concrete options). End your turn at the call.

**2. Target viewports (responsive).** `AskUserQuestion` (multiSelect): *"Which viewports should this design target?"* → **Phone / Tablet / Desktop / Wide** (default Phone + Desktop). Record the choice; the mockup will render the SAME design across those breakpoints.

**3. Emit the design system.** For the chosen direction:
   - `.workspace/shared/design-tokens.css` — Tier-1 primitives + Tier-2 semantics, with **both** light and dark maps (per design-tokens.md).
   - `.workspace/shared/brand.md` — chosen archetype, the **seed** (so it's reproducible / re-rollable) only when variation ran (greenfield or rework), otherwise `seed: n/a (followed current design)`, token values, and target viewports (template: [brand-book.md](brand-book.md)), and a **Guidelines applied** section (which guideline set, the sections consulted, deliberate deviations and why). Migrate an existing prose `brand.md` into this token format.

**4. Present the mockup — ONE design, light+dark, responsive.**
   - **Companion surface (B):** write `<design-dir>/screens/v1/mockup.css` (imports the tokens; components reference **only** `var(--semantic-*)` — never a primitive or raw hex) then `<design-dir>/screens/v1/mockup.html` (no `<style>` blocks). Ship a `[data-theme]` **light/dark toggle** so the user flips themes on the SAME screen (that's how they see it's one design, not two). Make it **responsive** across the chosen breakpoints (mobile-first + `@media (min-width:…)`). Apply the quality rules + multi-viewport preview harness in [visual-companion.md](visual-companion.md); preview each chosen viewport. Give the URL. End your turn; iterate with paired naming (`mockup-v2.css`+`.html`). When approved, capture it per theme and per chosen viewport as in [capture.md](capture.md).
   - **Artboard surface (A):** write the same `mockup.css` + `mockup.html` pair to disk (same rules). Then show it as one artboard per chosen viewport in the `/design` artifact, with the light and dark theme side by side. Give the artifact link. End your turn. Iterate on disk first, then update the artboards. When approved, record the artboard to `<design-dir>/screens/v<n>/`. The HTML pair is already there. Add the screenshots per [capture.md](capture.md), so the artifact is never the only copy.
   - **Text mode (C):** describe the layout, the token direction, how it adapts across the chosen viewports, and that light/dark share one design. Then call `AskUserQuestion` — *"Does this direction look right?"* — with options **Approve** / **Request changes**. End your turn at the call; treat free-form feedback as Request changes.

Before any mockup is shown, run the [review checklist](../../../lore/deep/design-principles.md#review-checklist) and fix every failing item; list the items you could not satisfy in the mockup description.

Self-check before serving: grep the mockup for raw `#hex`/`rgb(` outside the token blocks — if found, a component is bypassing the tokens (breaks theming/variation); fix it.

Only advance when the user explicitly approves the design.

**5. Offer `/design-sync` (once, after approval).** If the project has a design system of its own (a tokens file, a theme package or a component library with its own variables), say one sentence: *"Claude Code's bundled `/design-sync` can push `.workspace/shared/design-tokens.css` and `brand.md` into it — want me to run it?"* Run it only when the user says yes. It edits project files, so each write goes through Claude Code's normal permission prompt. This skill pre-approves none of them. Skip the offer when there is no design system to sync into. Never run it on your own.
