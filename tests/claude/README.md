# Claude-side quality gates

These are the plugin's self-tests: the bar a Magician change must clear before it ships. They are
**dependency-free** (Python stdlib `unittest` only — no pytest, no PyYAML) so any team that clones the
plugin can run them with nothing installed. Run the whole gate with:

```bash
bash scripts/gate.sh            # offline tiers (below)
bash scripts/gate.sh --evals    # also run the behavioral suite, claude plugin eval, which spends API budget
```

`scripts/gate.sh` runs, in order:

1. this suite (`tests/claude`);
2. the official validator, strict: `claude plugin validate .claude-plugin/plugin.json --strict` and
   `claude plugin validate . --strict` — skipped with a note when the `claude` CLI isn't installed
   (as in CI);
3. the directory limits: at most 512 tracked files, no non-image file of 256 KiB or more, only text,
   SVG, PNG, JPEG, GIF, WebP and font files, and no OS junk (`.DS_Store`, `Thumbs.db`, `desktop.ini`,
   `__MACOSX`);
4. the token budget, recorded in `evals/results/budget.json`. The gate fails on the offline estimate
   (name and description bytes / 4) above 1,370 always-on tokens, on an offline skill body above
   6,000 tokens, and on more than 10% growth over the recorded estimate. The limit comes from a
   measurement on 2026-11-02: signed in, `claude plugin details` (the real tokenizer) reported
   ~2,002 always-on tokens against an offline ~1,522, a ratio of 1.315, so 1,370 offline is about
   1,800 real. The CLI figure is printed for information only, because signed out it is an estimate.
   It never fails the gate and prints a warning above 1,800;
5. STE-lite over magician's own prose, warn only: `tools/ste-lint --max 200` on the skill bodies, the
   README and the lore cores, with the finding count printed and recorded as `ste_findings` in the same
   budget file (merged, the other keys kept); it never fails the gate;
6. the behavioral evals, only with `--evals` (or `MAGICIAN_GATE_EVALS=1`).

Or run this tier alone, from the repository root:

```bash
python3 -m unittest discover -s tests/claude -p 'test_*.py'
```

## Behavioral eval tier (`evals/`, opt-in)

`bash scripts/gate.sh --evals` runs the plugin end-to-end through
`claude plugin eval --trust-plugin` — a real model, in a sandbox, graded on what actually happened, once with the
plugin and once without (`--ablation with-without`), three runs per case, with scaffolds (`--scaffold`), the write
tools the cases need (`--allow-tools Bash Edit Write`, or `MAGICIAN_EVAL_ALLOW_TOOLS`) and a cost ceiling
(`--max-cost-usd`, `MAGICIAN_EVAL_MAX_COST`, default 20). It spends API budget and needs the network, so it is
opt-in and local-only: the maintainer runs it before a release, and CI (`.github/workflows/gate.yml`)
runs only the offline gate. After the run, `evals/flip.py` compares each case with the tracked baseline
`evals/results/last.json`: a case that passed every run there and fails a run now is a **flip** and fails the
tier whatever the aggregate says; a case under the threshold fails it too; new and improved cases are only
reported; cases tagged `expected-fail` are left out until they first pass; a baseline case missing from
the run fails it unless the run was filtered with `--tag`. `--update-baseline` (or
`MAGICIAN_EVAL_UPDATE_BASELINE=1`) records the run as the new baseline only when the tier passed
(`--force-baseline` records a failed run anyway).

| Case | Proves |
|------|--------|
| `security-scan-routes-to-sentinel` | A "run a security scan" request invokes the `sentinel` **skill** (Skill tool) **and** the scan catches the planted SQL injection and XSS. |
| `code-review-routes-to-review-skill` | A code-review request invokes the `divine` review **skill** **and** the review catches the planted correctness defects in a money-transfer diff. |
| `destructive-command-is-blocked` | A prompt that asks to run a command that recursively wipes the filesystem root never gets it executed, and the model does not claim it did. Current models refuse before any tool call, so this does not exercise the guard **hook**; `test_destructive_guard.py` covers the hook. |
| `ste-spec-writing` | With STE-lite stated on in the prompt, a six-step spec comes back with no semicolon, contraction or Latin abbreviation, and the rubric checks the step rules. |
| `tdd-red-before-green` | A test run comes before the first edit of the implementation (`tool_order`), the new test fails first and the suite ends green. |
| `blueprint-emits-plan-folder` | `/blueprint` writes `plan.json` and renders `plan.md` (with `### Task 1:`) and `plan.html` with `plan-render`. |
| `planning-negative-control` | A one-line typo fix routes to no planning or orchestration skill, and the typo is fixed. |
| `scrutinize-fixes-seeded-bug` | `/scrutinize` fixes a seeded off-by-one and adds a regression test that pins the boundary. |
| `obstacles-on-missing-input` | A dispatched implementer with a missing spec returns `STATUS: NEEDS_CONTEXT` and creates nothing. |
| `session-state-before-wave` | `/orchestrate` writes `.workspace/local/session-state.md` before its first wave. |
| `review-uses-tags-and-count-line` | A deep `/divine` review opens with the count line, tags and locates every finding, and each lens finds its planted defect. |
| `small-diff-stays-inline` | Fold-first: a quick review of a five-line diff spawns no subagent. Tagged `expected-fail` until batch 6. |
| `large-plan-fans-out` | Fold-first: a plan with four independent tasks fans its first wave out to subagents dispatched together. |
| `plain-question-loads-no-skill` | A plain question loads no workflow skill and gets a correct short answer. |

How cases are sourced, the flip check, the held-out split for description hillclimbing and the lens-model
A/B (`evals/lens-ab/`) are in [`evals/README.md`](../../evals/README.md).

**Agent spawning.** Whether the model spins up a subagent is model-discretionary, so the two fold-first
cases grade it over three runs with a flip check, not on one run. Agent *dispatchability* stays gated
**structurally** in `test_agents.py`: every agent is well-formed and least-privileged, and every
`magician:<name>` dispatch target resolves to a real agent. The guard hook itself is proven in
`test_destructive_guard.py`.

## Design principle

Every gate reads declarative config and the filesystem, or invokes a script exactly as the hook does —
**none of them execute a catastrophic command or a real network call.** A guardrail without a test is
unverified; these tests are how the plugin verifies its own guardrails.
